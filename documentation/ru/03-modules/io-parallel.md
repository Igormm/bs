# Модуль `io::parallel`

`lib/io/parallel` вызывает callback один раз для каждого элемента входного
списка или выполняет одну shell-команду на строку файла задач, ограничивая число
одновременно работающих воркеров.

Исходник: [lib/io/parallel.sh](../../../lib/io/parallel.sh) · Ярус: `@shell bash4,zsh`

## Загрузка

```bash
#!/usr/bin/env bs

load "lib/io/parallel"
```

Модуль работает в bash 4.2+ и zsh. Для zsh включаются `KSH_ARRAYS` и
`SH_WORD_SPLIT`, чтобы массивы с нулевым индексом и кавычки вокруг раскрытий
вели себя как в bash.

## API

```bash
io::parallel::map --jobs N --out-dir DIR [--scheduler pid|fifo|xargs] -- callback элемент...
io::parallel::run --jobs N --out-dir DIR [--scheduler pid|fifo|xargs] -- tasks.txt
io::parallel::cancel
```

- `--jobs N` и `--out-dir DIR` обязательны; `N` — положительное целое не больше
  `2147483647`.
- `--help` выводит справку в stderr и возвращает `E_SUCCESS`, не запуская работу.
- Разделитель `--` ровно один. После него идут callback и все элементы, поэтому
  элемент `--jobs` остаётся позиционными данными.
- `map` вызывает `callback` с одним элементом в `$1`. Аргументы не вычисляются
  и не разбиваются на слова; пробелы и переводы строк остаются внутри элемента.
- `run` читает одну команду из каждой непустой строки без комментария и
  выполняет её через `bash -c`. Пустые строки и комментарии, у которых первый
  непробельный символ — `#`, игнорируются. Файл задач — доверенный shell-ввод,
  а не данные, которые нужно экранировать.
- Пустой список элементов или файл только из комментариев/пустых строк
  возвращают успех и не создают файлов результатов.
- Публичные функции сохраняют чистый stdout. Диагностика идёт в stderr.

## Результаты

Результаты — файлы в `--out-dir`, с индексами от нуля в порядке входа:

| Файл | Содержимое |
|---|---|
| `NNNN.out` | stdout воркера |
| `NNNN.err` | stderr воркера |
| `NNNN.rc` | код завершения воркера в десятичном виде |

Индекс дополняется нулями минимум до четырёх цифр. Воркеры пишут в приватный
staging-каталог внутри `--out-dir`, после чего готовые файлы публикуются под
конечными именами через `mv -T` (без трактовки цели как каталога). Существующие
обычные файлы и другие записи, не являющиеся каталогами, заменяются; существующие
symlink заменяются без перехода по ним, а каталог вызывает `E_ERROR`.
Посторонние файлы и устаревшие индексы выше последнего не удаляются.

Ошибка одного воркера не останавливает остальные. После попытки выполнить все
задачи функция возвращает `E_ERROR`, а индивидуальные статусы остаются в `.rc`.

## Планировщики

| Планировщик | Поведение |
|---|---|
| `pid` | По умолчанию. Фоновые воркеры и `wait PID`; без зависимости, специфичной для планировщика. |
| `fifo` | Воркеры сообщают о завершении через FIFO; дополнительно нужен `mkfifo`. |
| `xargs` | Зарезервированная заглушка. Возвращает `E_ERROR` до создания каталога результатов и временного состояния. |

Оба реализованных планировщика помимо встроенных возможностей оболочки
используют стандартные утилиты `mkdir`, `mktemp`, `mv` и `rm`. Для безопасной
публикации нужен `mv` с поддержкой `-T` (её дают GNU coreutils и BusyBox).

## Коды возврата

- `E_SUCCESS` (`0`) — все воркеры успешны или работы не было.
- `E_INVALID` (`2`) — неверные опции, отсутствует callback/файл задач или файл задач недоступен для чтения.
- `E_ERROR` (`1`) — хотя бы один воркер завершился с ошибкой, результат не
  удалось записать, запрошена отмена, нет `mkfifo` или выбрана заглушка `xargs`.

## Отмена

SIGINT/SIGTERM останавливают активные PID воркеров, сохраняют каталог и уже
записанные файлы результатов, удаляют внутреннее FIFO/временное состояние,
восстанавливают прежние INT/TERM traps вызывающего и заставляют пул вернуть
`E_ERROR`. `io::parallel::cancel` программно запрашивает такую же очистку и сама
возвращает `E_SUCCESS`.

Состояние пула глобально для процесса: не вызывайте `io::parallel::map` или
`io::parallel::run` рекурсивно из воркера. Каждый callback выполняется в
подконтрольном дочернем процессе, поэтому `exit` и `exec` внутри callback всё
равно дают результат и FIFO-completion. Если callback запускает дальнейшие
потомки, он должен сам организовать их завершение: отмена направляется дочернему
процессу callback и зарегистрированному PID воркера.

## Примеры

```bash
load "lib/io/parallel"

my_worker() {
    printf 'item=%s\n' "$1"
    printf 'diagnostic=%s\n' "$1" >&2
}

io::parallel::map --jobs 4 --out-dir results -- \
    my_worker alpha "two words" $'line1\nline2'

io::parallel::run --jobs 4 --scheduler fifo --out-dir results -- tasks.txt
```

Пример файла задач для `run`:

```bash
# комментарии и пустые строки игнорируются
printf 'first\n'
printf 'second\n' >&2
false
printf 'still runs\n'
```

Рабочее демо: [examples/parallel_demo.sh](../../../examples/parallel_demo.sh).
