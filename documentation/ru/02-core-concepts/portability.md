# Портируемость и вектор возможностей — рекомендации

> Рекомендации по поддержке разных платформ (GNU/Linux, macOS, FreeBSD,
> busybox/Alpine) и версионированию проекта по векторам возможностей.
> Обязательные правила — в code-style-guide §11; этот документ — полное
> описание и обоснование.

## 1. Зачем это

Проект BS работает на bash 4+ и претендует на «вездесущность». Но
«везде» — это разные миры:

- **GNU/Linux** — `grep -P`, `sed -z`, `sha256sum`, `stat -c`, `/proc`, `/sys`;
- **macOS и FreeBSD (BSD userland)** — `shasum`, `stat -f`, нет `grep -P` и `sed -z`, нет `/proc`/`/sys`;
- **Alpine (busybox)** — минимальный набор, `apk` вместо `apt`;
- **musl против glibc** — различия в основном на уровне бинарников, для bash-скриптов малозначимы.

Имя ОС ничего не говорит о возможностях: GNU/Linux бывает glibc и musl,
с `/sys` и без, с `grep -P` и без. Поэтому **версионируем по вектору
возможностей, а не по именам платформ**.

## 2. Вектор возможностей

Вектор — набор фактов о текущем окружении:

```
kernel      — linux | darwin | freebsd
arch        — x86_64 | aarch64 | ...
distro      — ubuntu | fedora | ... (ID из /etc/os-release)
family      — debian | rhel | suse | arch | alpine (ID_LIKE-цепочка)
repo        — apt | dnf | apk | pacman | zypper | brew | pkg (производное от family)
userland    — gnu | bsd | busybox
libc        — glibc | musl
bash        — версия
tools       — наличие sha256sum/shasum/cksum, grep -P, sed -z, stat -c, ...
fs          — /proc, /sys, /sys/class/dmi, ...
root        — есть ли привилегии
```

Репозиторий пакетов — всегда производное от `family` (ID_LIKE), а не от
названия дистрибутива: Ubuntu и Mint оба наследуют `debian` → `apt`.

## 3. Алгоритм детекции (каскад)

1. `uname -s` → ядро;
2. `/etc/os-release` → `ID`, `VERSION_ID`;
3. `ID_LIKE` → семейство;
4. пробы инструментов → userland и возможности;
5. проверки среды (`[[ -d /proc ]]`, `id -u`) → финальные биты.

Каждый шаг не зависит от предыдущего: инструментальные пробы делаются
всегда, они сами определяют userland.

## 4. Фича-детекция и probe chains

Проверяй способность, а не имя. Эталон — `bs_build::sha256`:

```bash
sha_cmd="$(platform::probe "sha256sum" "shasum -a 256" "cksum")"
```

GNU-only инструменты и их fallback:

| Инструмент | GNU (Linux) | BSD (macOS/FreeBSD) | Fallback-цепочка |
|---|---|---|---|
| Хеш | `sha256sum` | `shasum -a 256` | `sha256sum → shasum → cksum` |
| PCRE | `grep -P` | — | `grep -P` → ERE (`grep -E`) |
| Многострочный sed | `sed -z` | — | `sed -z` → `perl -0` |
| Размер файла | `stat -c %s` | `stat -f %z` | проба поведения |
| Наносекунды | `date +%N` | — | `date +%N` → `date +%s` + 000 |
| readlink | `readlink -f` | нет в macOS | `readlink -f` → `realpath` → цикл |

## 5. Стратегии версионирования

**Рекомендуется**: единый репозиторий + capability-гейты + слои
совместимости (`lib/platform/compat/*`). Отдельные репозитории под
платформы оправданы только при глобально разных рантаймах.

Тиры совместимости (для версии и `bs doctor`):

- `core` — чистый bash 4+, без GNU-инструментов: работает везде;
- `gnu-linux` — GNU userland (`grep -P`, `sed -z`, `sha256sum`);
- `posix` — только POSIX-инструменты (fallback-режим);
- `bsd` — macOS/FreeBSD слои совместимости.

Скрипт при старте проверяет нужный тир и падает с понятной ошибкой,
если возможности нет (вместо криптопада из-за `sed -z`).

## 6. Дистрибутивы и репозитории пакетов

| ID | Семейство | Репозиторий |
|---|---|---|
| ubuntu / debian / mint | debian | apt |
| fedora / almalinux / rhel | fedora | dnf/yum |
| alpine | alpine | apk |
| arch | arch | pacman |
| opensuse | suse | zypper |
| macOS | — | brew |
| FreeBSD | — | pkg |

**План (на будущее)**: публикация BS как пакетов apt/dnf/brew — отдельная
инфраструктура (подпись, репозитории, формулы); на данном этапе
достаточно `install.sh` и `bs build`. Структура `lib/platform/repo.sh`
(карта семейство → команда установки) закладывается уже сейчас.

## 7. Минимальная поддерживаемая платформа (контракт)

Фиксируем матрицу поддержки явно (проверяется `bs doctor`):

| Тир | Требования |
|---|---|
| `core` | bash 4.0+, POSIX-инструменты, Linux-подобная ФС |
| `gnu-linux` | тир core + GNU userland (grep -P, sed -z, sha256sum) |
| `bsd` | тир core + bash 4+ из пакетов (системный bash на macOS — 3.2!) |

Замечание: системный bash на macOS — 3.2 (лицензия GPLv2), поэтому
macOS-поддержка подразумевает bash из Homebrew. На данном этапе macOS —
вне приоритета.

## 8. Тестовые хуки для платформо-зависимых путей

Платформенные данные нельзя читать напрямую в тестах, поэтому каждый
модуль с `/sys`-зависимостями получает **хуки-переопределения путей**
(переменные окружения с дефолтами):

```bash
: "${HW_DMI_PATH:=/sys/class/dmi/id}"     # lib/system/hw
: "${SSH_MOCK:=}"                          # lib/network/ssh — мок-бинарник
: "${LLM_MOCK_RESPONSE:=}"                 # lib/integration/llm — мок-ответ
: "${MATH_CACHE_DIR:=...}"                 # lib/math — изолированный кэш
```

Паттерн: `: "${VAR:=реальный_путь}"` при загрузке модуля + тест
подменяет переменную и вызывает `module::reset` (при наличии) или
перезагружает модуль. Это позволяет тестировать логику без реального
железа и без прав root.

## 9. Кэш фактов

Сбор вектора возможностей — быстрая операция (миллисекунды), но для
сотен скриптов в CI ощутима. Факты кэшируются в
`${XDG_CACHE_HOME:-$HOME/.cache}/bs/facts` и пересобираются при
изменении окружения (хеш ключевых файлов: uname, os-release).

## 10. Итог

1. Детекция: каскад `uname → os-release → ID_LIKE → пробы`.
2. Выбор реализации: probe chains, никогда `uname`-ветвление.
3. Версионирование: единый репо, capability-гейты, тиры core/gnu-linux/bsd.
4. Тесты: хуки-переопределения путей, изолированные кэши.
5. Контракт: матрица поддержки проверяется `bs doctor`.
