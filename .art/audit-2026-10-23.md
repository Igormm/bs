### P1 — release blocker для OpenBao

#### 1. Визард prod-сервера не проверяет `jq`

- `examples/openbao_wizard.sh:224-229`: `check_server_tools` проверяет
  `tar`, `sha256sum`, `gzip`, `curl|wget`, `systemctl`, `useradd`, но не `jq`.
- `lib/system/openbao.sh:647-651`: `openbao_server::unseal` требует `jq`.
- `lib/system/openbao.sh:21`: `@optdeps` тоже не содержит `jq`.
- `documentation/en/03-modules/system-openbao.md:149-150` и ru-двойник:
  зависимости перечислены без `jq`.

Сценарий: минимальная AlmaLinux без `jq` (именно так было в реальном smoke) →
визард проходит preflight, ставит бинарник, создаёт пользователя, конфиг,
systemd-юнит, делает `operator init` и пишет init-файл, затем падает на
`unseal` с `LIB_ERROR_DEPENDENCY_MISSING`. Сервер остаётся sealed, а
пользователь узнаёт о зависимости слишком поздно.

Ожидаемо: `jq` в `check_server_tools` и в документации/`@optdeps`, либо
явная проверка в `apply prod` до установки.

#### 2. TLS `files`: сервис может не прочитать ключ

- `lib/system/openbao.sh:526-530`: для `BS_OPENBAO_TLS_MODE=files` проверяется
  только `-r` сертификата и ключа от текущего пользователя (обычно root).
- `lib/system/openbao.sh:470-473`: chown ключа на service-пользователя есть
  только в selfsigned-ветке.
- `examples/openbao_wizard.sh:317-321`: визард делает ту же проверку `-r`.

Сценарий: ключ `0600 root:root` (типично для существующего TLS) проходит
проверку под sudo, но systemd запускает OpenBao как `openbao`; сервис падает
на чтении ключа. Ожидаемо: проверка от имени service-пользователя либо
явный chown/копирование с понятной ошибкой.

#### 3. TLS `files` + private CA ломает `operator init`

- `lib/system/openbao.sh:620-623`: `init_cluster` выставляет `BAO_CACERT`
  только для `selfsigned`.
- `lib/system/openbao.sh:595-596`: `__client_init` для `files` подставляет
  `BS_OPENBAO_TLS_CA`; `:696` делает то же для `status`.
- `examples/openbao_wizard.sh:310-321`: для `files` спрашиваются только
  cert/key, CA не спрашивается.

Сценарий A: cert подписан приватным CA, путь к CA передан в
`BS_OPENBAO_TLS_CA` → `wait_ready` может пройти, но `bao operator init` идёт
без `BAO_CACERT` и падает после запуска сервиса.

Сценарий B: cert подписан публичным CA, `BS_OPENBAO_TLS_CA` оставлен по
умолчанию (`/etc/openbao/tls/ca.crt`) и файла нет → `wait_ready` падает на
проверке TLS ещё до init.

Ожидаемо: для `files` использовать CA только если файл существует/задан,
передавать его в `init_cluster`, а визарду дать поле CA или явно объяснить
public-CA сценарий.

### P2 — функциональные дефекты

#### 4. Сломанный `bao` считается установленным

`lib/system/openbao.sh:315-323`:

```bash
current="$(openbao_server::version)" || current=""
if [[ -x "${BS_OPENBAO_BIN}" ]] && { [[ "${wanted}" == "latest" ]] || [[ "${current}" == "${wanted#v}" ]]; }; then
    log::info "OpenBao уже установлен / already installed: ... (${current:-unknown})"
    return 0
fi
```

Проверено на fake-бинарнике с `exit 1`:

```text
BS_OPENBAO_VERSION=latest
openbao_server::install
INFO OpenBao уже установлен ... (unknown)
install: rc=0 (skipped)
```

То есть `install` не может починить сломанный/несовместимый бинарник при
`latest`. Ожидаемо: `latest` + неработающий `version` → переустановка, а не
success.

#### 5. `BS_OPENBAO_GROUP` фактически не поддерживается

- `lib/system/openbao.sh:384-402`: `ensure_user` всегда вызывает
  `useradd --system --user-group "${BS_OPENBAO_USER}"`; группа
  `BS_OPENBAO_GROUP` не создаётся и не проверяется.
- `lib/system/openbao.sh:134`, `:163`: `__dir`/`__write_file` делают chown на
  `${BS_OPENBAO_USER}:${BS_OPENBAO_GROUP}`.

При кастомной группе, отличной от имени пользователя, первый chown падает или
файлы остаются с неверной группой. Ожидаемо: поддержать отдельную группу
(`groupadd`, `--gid`, проверка существования) или убрать hook из документации.

### P3 — безопасность, устойчивость, UX

6. **Окно прав на TLS-ключи.** `openssl` создаёт `ca.key`/`server.key` до
   `chmod 600` (`lib/system/openbao.sh:452-468`). При umask 022 ключи на
   короткое время доступны группе каталога `0750`; CA-ключ должен быть
   `root:root 0600` сразу. Ожидаемо: `(umask 077; openssl ...)`.

7. **Режим token-файла не проверяется.** `openbao::__read_token_file`
   (`lib/integration/openbao.sh:129-135`) читает любой readable-файл, хотя
   документация обещает `0600`. Ожидаемо: предупреждение/отказ, если файл
   доступен группе/остальным.

8. **Backup-коллизия.** `__backup` использует timestamp с точностью до секунды
   (`lib/system/openbao.sh:178-180`); два configure в одну секунду пишут в
   один `.bak.<ts>`. Ожидаемо: `mktemp`/PID/наносекунды.

9. **`status` в финальной подсказке без env.** `obw::final_server`
   (`examples/openbao_wizard.sh:455-456`) предлагает `sudo bao status` без
   `BAO_ADDR`/`BAO_CACERT`; при нестандартном listen или selfsigned команда
   не работает. Ожидаемо: показывать обе переменные или готовую команду.

10. **`apply dev` без токена.** Прямой `openbao_server::apply dev` логирует
    `dev_command` с пустым `BS_OPENBAO_DEV_TOKEN` (`lib/system/openbao.sh:723-727`);
    токен генерирует только `dev_start`/визард. Ожидаемо: генерировать в
    `apply dev` или явно требовать токен.

11. **`render_config` не валидирует profile.** `openbao_server::render_config`
    (`:481-494`) принимает любое значение и для неизвестного профиля ведёт себя
    как `prod`; `apply` при этом валидирует. Ожидаемо: общий валидатор
    `dev|prod`.

12. **Мёртвая ветка в визарде.** `examples/openbao_wizard.sh:230-232`
    проверяет `openssl` для dev только при `TLS_MODE != off`, но dev
    принудительно ставит `off` (`:259-260`). Ветка недостижима; очистить.

13. **Тестовые пробелы.** Нет тестов для:
    - TLS `files` и `off`;
    - отсутствующего `jq` в preflight;
    - кастомного `BS_OPENBAO_GROUP`;
    - сломанного `bao` при `latest`;
    - `files` + private/public CA.

    Текущие 140 OpenBao-тестов (37 client, 72 server, 31 wizard) проходят, но
    перечисленные P1/P2-ветки ими не покрыты.

14. **Валидатор сканирует `.claude/worktrees`.** `tests/validateshellcheck.sh:42`
    использует `find .` без исключения `.claude`; 2182 untracked копий
    превращают полный прогон в >1 ч. Ожидаемо: `git ls-files` или исключение
    `.claude/` (и других локальных worktree-каталогов).
